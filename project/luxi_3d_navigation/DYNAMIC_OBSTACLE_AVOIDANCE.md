# D1 动态避障设计与分阶段测试方案

## 1. 先说清楚具体怎么实现

这里的“动态避障”不要求先识别出“这是人”或“这是箱子”。更可靠的做法是：

1. 保存下来的 OctoMap 和 PLY 继续作为**全局静态地图**，负责楼层、坡面、台阶、坑区和长距离路线；
2. D435i 的实时深度图持续生成机器人周围的**滚动 3D 障碍层**，只保留最近一小段时间的观测；
3. 新出现的箱子、椅子或行人进入局部障碍层，消失后由空闲射线和时间衰减清除，不写回保存地图；
4. 局部规划器检查当前路径前方是否会碰到膨胀后的障碍：有空间就短距离绕开，再接回原全局路径；没有安全通路就停车等待；
5. 在路径跟随器和现有速度仲裁器之间增加一个独立的**速度安全门**。即使规划器阻塞、深度中断或 TF 过期，安全门仍能及时输出零速度。

可以把它理解为：静态地图是“提前准备好的路线图”，实时深度是“机器人眼前不断擦写的小草稿”，安全门是“最后一道刹车”。不需要每看到一个人就重新建立整张地图。

建议分三步上线：

- 第一期：只监测并停车，不自动绕行；
- 第二期：加入局部绕行和重新接回全局路径；
- 第三期：确有需要时才加入运动目标跟踪和速度预测。

## 2. 当前系统为什么避不开新障碍

当前导航的数据流是：

```text
保存的 .bt/.ply
      │
      ▼
地面支撑 3D A* ──> /navigation/planned_path
                           │
                           ▼
                    terrain_path_follower
                           │ 15 Hz
                           ▼
                    /navigation/cmd_vel
                           │
网页手动速度 ───────> velocity_command_mux ──> /cmd_vel ──> D1
```

`octomap_3d_astar_planner_node` 只订阅保存地图发布的 `/navigation/octomap`。收到目标后，它按这张静态地图规划一次；`terrain_path_follower_node` 随后只看路径、定位和 TF，并不订阅实时深度或局部障碍。因此，在建图之后放到路上的物体不会出现在路径碰撞检查中。

当前已有的安全能力可以复用：

- 跟随器以 15 Hz 输出导航速度；
- 定位或地形位姿过期、偏离路径时，跟随器会输出零速度；
- 速度仲裁器有 0.3 秒导航命令看门狗；
- `/navigation/emergency_stop` 能强制停止导航；
- 网页手动命令会抢占并结束自动导航。

缺少的是“实时障碍感知 + 局部路径碰撞检查 + 局部重规划”。

## 3. 从 `demo` 中参考到了什么

主要参考实现是 `demo/SCAN-Planner-Ros2`。它的核心不是语义识别，而是以下闭环：

```text
深度图或激光点云 + 同时刻传感器位姿
                 │
                 ▼
        射线更新滚动 3D 占据栅格
                 │
                 ▼
      按机器人双圆柱体积膨胀障碍
                 │
                 ▼
   高频采样未来 B-spline，检查碰撞
           │                 │
       较远有碰撞          即将碰撞
           │                 │
         重规划            紧急停止
```

其中可直接借鉴的思想包括：

- 5 cm 分辨率滚动体素地图；
- 深度端点记为“命中”，相机到端点之间的射线记为“空闲”；
- 用多帧概率而不是单帧点云决定体素是否占据，降低深度噪声误报；
- 按机器人实际空间体积膨胀障碍，而不是把机器人当成一个点；
- 路径执行期间持续检查未来轨迹，远处碰撞先重规划，近处碰撞进入紧急停止；
- Mode 3 用已有全局参考路径引导局部规划，适合“全局地图 + 局部避障”的结构。

SCAN 默认参数中，滚动地图为 `10 × 10 × 5 m`、局部更新范围为 `5 × 5 × 2.5 m`、深度范围为 `0.3～3.0 m`，地图和可视化更新周期均为 50 ms。未来轨迹按 0.01 秒采样，默认碰撞时间不足约 1 秒时进入紧急停止。

但 SCAN 不能原样接到 D1：

- 默认最大速度 `0.75 m/s`，而当前 D1 跟随器上限是 `0.10 m/s`；
- 它按四足机器人连续 3D B-spline 和双圆柱机身建模，D1 当前按平面 `x/y/yaw` 跟随地面路径；
- SCAN 闭环控制会输出平面 `linear.x`、`linear.y` 和 `angular.z`，而当前 D1 配置不使用横移；
- 它期望高频、时间同步的传感器位姿。当前全局 HLoc/ICP 绝对定位较慢，实时避障应主要依靠 `/navigation/odom` 的局部连续位姿；
- 检查到的 SCAN 占据更新依赖射线“miss”和滚动地图移出范围，没有单独的按墙钟时间衰减。物体移走后若被遮挡，可能形成短时残影；
- SCAN 自带 `dynamic.*` 参数是仿真器里的移动障碍生成器，不是行人识别或未来轨迹预测算法；
- `demo/COLCON_IGNORE` 会让根工作空间的普通构建跳过整个 demo，它目前是参考/独立实验工程，不是 D1 主工程的一部分。

所以本项目应复用它的“滚动体素、射线清空、膨胀、持续碰撞检查和重规划状态机”，而不是直接复制默认控制器和参数。

`demo/jie_3d_nav` 主要展示静态 OctoMap、A* 和路径执行，对保存地图导航有参考价值，但没有解决实时障碍的消失、局部重规划和运动预测，不应作为本次动态避障的主方案。

## 4. 可选方法及优缺点

| 方法 | 能发现新物体 | 能自动绕行 | 3D 净空/低矮障碍 | 优点 | 主要问题 | D1 建议 |
| --- | --- | --- | --- | --- | --- | --- |
| 深度最近距离/安全扇区 | 是 | 否 | 较弱 | 最简单、延迟低、容易先验证停车 | 椅腿/地面噪声容易误报，不知道往哪边绕 | 第一期必须有，作为独立保险 |
| 2D 局部代价地图 | 是 | 是 | 一般 | 算法成熟、算力低、调试直观 | 楼梯、悬空物、不同高度障碍会被压成平面 | 平坦区域可用，但不能单独承担 3D 地形导航 |
| 滚动 3D 体素 + 局部 2.5D/Hybrid A* | 是 | 是 | 好 | 与现有 5 cm OctoMap、地形层和 D435i 最匹配 | 需要正确的相机外参、地面过滤、衰减和局部规划 | **推荐主方案** |
| 完整移植 SCAN B-spline | 是 | 是 | 好 | 轨迹平滑，持续重规划，已有仿真框架 | 接口和运动学改造大；默认参数不适合 D1；定位要求高 | 作为后续优化/对照实验，不作为第一版 |
| Nav2 Voxel/STVL + DWB/其他局部规划器 | 是 | 是 | 中到好 | 生态和诊断工具完整，STVL 支持衰减 | 当前工程不是 Nav2；与现有 3D 地形 A*、HLoc/ICP 状态机整合成本高 | 若以后统一迁移 Nav2 再采用 |
| 目标检测 + 聚类跟踪 + 轨迹预测 | 是 | 是 | 取决于深度 | 可提前避让横穿行人，行为更自然 | 误检、遮挡、算力和调参成本最高，不能替代几何安全层 | 第三期可选，绝不能作为唯一保险 |
| 把实时点云直接融合进永久 OctoMap | 是 | 重新全局规划后可 | 好 | 改动表面上最少 | 移动物体容易留“鬼影”，污染保存地图，全图更新开销大 | 不推荐作为主方法 |

结论：采用“滚动 3D 体素 + 局部路径修补 + 独立深度停车”最适合当前工程。2D 压缩层可以作为局部规划加速结构，但原始 3D 体素仍要用于净空和安全检查。

## 5. 推荐的工程结构

### 5.1 数据流

```text
                         保存的 OctoMap / PLY / 语义坑区
                                      │
                                      ▼
目标 ───────────────────────> 全局地面支撑 3D A*
                                      │ /navigation/global_path
                                      ▼
实时深度 + CameraInfo ──> 滚动 3D 障碍层 ──> 局部路径修补器
       │                         │             │
       │                         │             └─> /navigation/planned_path
       │                         ▼                         │
       └────────────────> 直接安全走廊检查                ▼
                                                  terrain_path_follower
                                                           │ raw cmd_vel
                                                           ▼
                                                    速度安全门
                                                           │ safe cmd_vel
网页手动速度 ─────────────────────────────────────> 现有速度仲裁器
                                                           │
                                                           ▼
                                                        /cmd_vel
```

### 5.2 已实现组件

代码已放在 `luxi_3d_navigation`，没有让机器人 SDK 桥接层承担感知和规划职责。

1. `local_obstacle_map_node`
   - 订阅 `/sensors/rgbd/depth/image_raw`；
   - 订阅 `/sensors/rgbd/color/camera_info`；
   - 使用 TF 或同步里程计获取深度帧时刻的相机位姿；
   - 输出局部占据点、传感器健康状态和最近障碍距离；障碍膨胀在局部规划器内部完成，避免重复发布大点云。

2. `local_path_replanner_node`
   - 输入静态全局路径和滚动障碍层；
   - 在机器人前方局部窗口寻找绕行段；
   - 重新接回原全局路径，输出跟随器使用的路径；
   - 找不到路径时保持阻塞状态，不生成冒险路径。

3. `navigation_safety_gate_node`
   - 输入跟随器原始速度、深度健康、局部障碍和重规划状态；
   - 输出限速或零速度给现有 `velocity_command_mux_node`；
   - 任何输入超时都按启用配置进入 fail-safe；
   - 普通“前方暂时被挡”保持零速并等待重规划；传感器失效或内部异常会锁住安全门并发布 `/navigation/safety_hard_stop=true`，需要停止并重新开始导航才能复位。

现有 `/navigation/emergency_stop` 保留给网页人工急停，触发后速度仲裁器会结束导航并向跟随器发布 `/navigation/stop`。安全门不能与网页同时向该话题反复发布 true/false，否则一个发布者可能清掉另一个发布者的急停。因此动态避障只把审核后的导航速度送入仲裁器，硬故障状态使用独立的 `/navigation/safety_hard_stop`；安全门进程退出时，仲裁器现有的 0.3 秒导航命令看门狗仍会输出零速度。

### 5.3 建议的话题分工

下表接口已经接入 `saved_map_navigation.launch.py`：

| 话题 | 类型 | 作用 |
| --- | --- | --- |
| `/navigation/global_path` | `nav_msgs/msg/Path` | 静态地图生成的长距离路径 |
| `/navigation/planned_path` | `nav_msgs/msg/Path` | 局部修补后交给跟随器的路径 |
| `/navigation/cmd_vel_raw` | `geometry_msgs/msg/Twist` | 跟随器未经安全门处理的速度 |
| `/navigation/cmd_vel` | `geometry_msgs/msg/Twist` | 安全门输出，继续接现有速度仲裁器 |
| `/navigation/local_obstacles/points` | `sensor_msgs/msg/PointCloud2` | 调试用实时障碍点；无人订阅时不必发布 |
| `/navigation/local_obstacles/state` | `std_msgs/msg/String` | `clear/slow/blocked/stale/error` |
| `/navigation/local_obstacles/nearest_distance` | `std_msgs/msg/Float32` | 相机前方安全走廊内的最近障碍距离 |
| `/navigation/local_replan/status` | `std_msgs/msg/String` | `idle/planning/ready/no_path` |
| `/navigation/safety_limited` | `std_msgs/msg/Bool` | 当前速度是否被安全门限制 |
| `/navigation/safety_hard_stop` | `std_msgs/msg/Bool` | 传感器/状态硬故障锁停；与人工急停话题隔离 |

调试点云只在 RViz 或录包需要时发布，网页继续只显示 RGB，避免再次把大点云压到网页链路上影响控制连续性。

## 6. 关键算法和首轮参数

以下数值是安全起步值，不是已经标定好的最终参数。真机通过分阶段测试后才能固化。

### 6.1 深度和位姿

- 深度处理频率：目标 `10 Hz` 左右；当前 D435i 保持约 29～30 Hz 原始深度，订阅端只保留最新一帧，按 12 像素采样和稀疏空闲射线后，本机实测障碍状态稳定约 10.0 Hz；
- 有效距离：先用 `0.25～2.5 m`，超出范围只用于空闲射线，不当成障碍端点；
- 体素分辨率：`0.05 m`，与现有静态 OctoMap 对齐；
- 局部窗口：机器人前方约 `3.0 m`、后方 `0.5 m`、左右各 `1.5 m`，高度范围覆盖脚、腿和机身；
- 即时停车检查尽量在 `base_link` 局部坐标完成，不依赖较慢的全局重定位；
- 局部重规划使用 `/navigation/odom` 的连续位姿，并由 `map -> odom` 把局部障碍与全局路径对齐；
- 深度、CameraInfo、TF 和里程计必须检查时间戳。本机 D435i 深度会领先 2 Hz 全局定位 TF 约 0.03～0.10 s，因此实现先检查深度帧年龄，再用同一份最新 `map -> base_link` 与静态 `base_link -> camera` 组成一致变换；不能分别取三个不同时刻的 TF；
- 深度或障碍状态超过 `0.60 s` 未更新时，启用动态避障的导航必须输出零速度。D1 最小有效步态为 0.10 m/s，对应最坏额外行程约 0.06 m。

`/navigation/odom` 的实际频率和稳定性必须现场测量，不能仅根据 launch 参数假定它足够快。全局 HLoc/ICP 用来限制长期漂移，局部里程计用来保证相邻深度帧连续。

### 6.2 占据和清除

- 至少连续 2 帧命中再把体素标成障碍；特别近的障碍可单帧直接进入紧急区；
- 空闲射线连续观测 2～3 次后清除占据；
- 显式空闲射线看到障碍移走时仍立即降低占据分数；没有被相机重新观察到的体素保留 `30 s`，条目 `35 s` 后清理。该值匹配 D1 的 0.10 m/s 低速和 3 m 滚动窗口，避免绕行转向后障碍离开相机视场便被过早遗忘；
- 只对当前相机可见射线做“miss”清空，不能把遮挡物后方误判为空闲；
- 过滤相机无效值、深度突变边缘、机器人自身、地面和足端附近固定结构；
- 对黑色、反光、透明物体和细椅腿单独测试。深度为 0 不能简单理解为“没有障碍”。

时间衰减太短会让短时遮挡后的障碍突然消失；太长会让移走的箱子在地图中留下鬼影。推荐值必须用录包重放和真机移物测试确定。

### 6.3 障碍膨胀和停车距离

静态配置中的 `robot_radius=0.25 m` 来自当前中心到轮子的实测距离，不能直接等同于动态避障的安全半径。动态层的初始膨胀建议按：

```text
横向安全半径 = 实测最大机体/腿部外廓半径 + 0.10～0.15 m 余量
停车距离 = max(固定最小值,
               当前速度 × 总反应时间
               + 当前速度² / (2 × 实测减速度)
               + 深度/定位误差余量)
```

在最大 `0.10 m/s` 尚未做制动标定前，前向硬停车距离先取不小于 `0.45 m`，减速区先取约 `0.70 m`。这两个值看起来保守，但前视相机有近距离盲区，且 D1 步态不会像轮式底盘一样瞬间停住。完成不同速度下的实测制动距离后再缩小。

### 6.4 局部绕行

D1 当前跟随器的实际运动是“转向 + 前进”，没有使用横移，所以不应直接输出 SCAN 默认的 `linear.y`。建议：

- 从当前全局路径上取前方 `1～3 m` 作为局部参考；
- 将静态可通行地形、语义坑区和动态膨胀体素投影成带高度/坡度约束的 2.5D 层；
- 使用带航向状态的 Hybrid A* 或保守的格点 A* 生成“先转、再前进”的局部路径；
- 候选路径仍用原始 3D 体素检查机身净空，防止只看地面投影；
- 选择障碍后方的可见全局路径点作为重新汇合点；
- 规划频率先用 `2～5 Hz`，碰撞检查保持 `10～20 Hz`；
- 找不到路径时停车，不允许穿越 unknown、坑区或静态不可通行地形；
- 路径连续无障碍至少 `0.5 s` 后才允许自动恢复，避免占据阈值附近反复启停。

### 6.5 状态机

建议明确使用以下状态，而不是用一个布尔值包办所有情况：

```text
MONITOR_ONLY  只报告，不影响速度
TRACKING      路径安全，正常跟随
SLOWING       障碍进入减速区
BLOCKED       障碍进入停车区，保持零速并请求重规划
REPLANNING    零速等待局部新路径
RECOVERING    新路径或原路径连续安全后准备恢复
HARD_STOP     深度/TF/里程计超时、内部异常或人工急停；需人工确认
```

## 7. 分阶段测试方法

测试顺序不能颠倒。先用软箱、泡沫板等可碰撞测试物，最后才测试行人横穿。全程安排一人持官方遥控器/急停并站在机器人侧后方，不站在预期路径上。

### 7.1 第 0 级：离线单元测试和录包回放

不连接 D1 运动控制，测试：

- 深度像素投影到 `base_link` 后方向、高度和尺度正确；
- 同一障碍连续命中后占据，移走后能在目标时间内清除；
- 射线不会清除障碍后方的未知区域；
- 地面、机器人自身和无效深度不会触发停车；
- 膨胀半径覆盖机器人外廓；
- 给定路径与体素相交时一定进入 `blocked`；
- 深度、TF、里程计分别超时都会输出零速度；
- 局部规划找不到路径时不会沿旧路径继续走；
- 速度门对 NaN、无穷值、过期命令和异常状态输出零速度。

用真实场景录包做可重复回归：

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=42

ros2 bag record -o dynamic_avoidance_input \
  /sensors/rgbd/depth/image_raw \
  /sensors/rgbd/color/camera_info \
  /sensors/imu/data \
  /sensors/rgbd/rgbd_image \
  /navigation/odom \
  /tf /tf_static
```

回放时保持 SDK 关闭，使用 `monitor_only:=true`。录包不应包含用户名、密码或网页令牌。

### 7.2 第 1 级：静止台架监测

机器人趴下或站立但 SDK 运动关闭，先不让安全节点接管速度。

1. 相机前方由远到近放置软箱；
2. 从 RViz 或状态话题观察 `clear -> slow -> blocked`；
3. 左右移动箱子，确认坐标方向和安全走廊一致；
4. 移走箱子，记录鬼影清除时间；
5. 遮住相机、停止深度话题、制造 TF 过期，确认进入 `stale/HARD_STOP`；
6. 测试地面、桌腿、低矮物、悬空横杆、黑色和反光表面。

通过条件：100 次放入/移出中不漏掉进入硬停车区的普通不透明软箱；传感器超时一定报告停止；静止场景没有持续高频状态抖动。

### 7.3 第 2 级：10 cm～1 m 短距离停车测试

这是第一次允许机器人运动，只启用停车，不启用自动绕行。

- 空旷平地，先下发约 10 cm 的低速直线路径；
- D1 实测 `0.05 m/s` 基本不产生有效前进，因此首次有效运动使用其最小步态 `0.10 m/s`；不能用发送无效小速度来代替停车距离和安全门；
- 先在启动前放好软箱，确认机器人拒绝前进；
- 再让机器人前进 0.5～1 m，由侧面把带长柄的泡沫板送入路径；
- 分别在 0.8 m、0.6 m、0.45 m 处进入，测检测延迟、零速发布时间和最终停车距离；
- 障碍移走后，第一期要求人工重新开始，防止意外自动恢复；
- 当前最小有效速度和上限均为 `0.10 m/s`，需要直接在该速度下标定停车距离。

通过条件：机器人外廓不接触障碍；`/cmd_vel` 在进入硬停车条件后持续为零；相机断流、节点崩溃和定位断流均不能让上一条速度继续保持。

### 7.4 第 3 级：2～3 m 局部绕行

停车层通过后才启用局部重规划：

1. 在 2～3 m 直线路径中间放宽软箱，两侧至少留出一条明确安全通道；
2. 分别测试只能从左侧、只能从右侧、两侧均可通过；
3. 用横向长障碍封死全部通道，必须停车并报告 `no_path`；
4. 障碍移走后验证占据清除和恢复条件；
5. 在起点、路径中段、接近目标处分别插入障碍；
6. 重复测试障碍贴近静态墙面、坡道边缘和语义坑区的情况，局部规划不得为绕动态障碍而进入静态禁区。

通过条件：绕行路径始终保留规定净距；新路径能稳定接回全局路径；不存在左右反复选择、原地高频转向或新旧路径来回切换。

### 7.5 第 4 级：移动障碍测试

先用移动泡沫板或纸箱小车，再由人员横穿：

- 垂直横穿路径；
- 同向慢速移动；
- 从视野边缘突然进入；
- 进入后停住；
- 短暂遮挡后再次出现。

纯几何滚动体素能对“已经观测到的位置”避障，但不会预测人下一秒走到哪里。因此第一、二期的正确行为可以是保守停车，不以“始终流畅绕过行人”作为验收要求。

### 7.6 第 5 级：10～20 m 人工长距离测试

- 选择平整、照明稳定、无楼梯坠落风险的封闭路线；
- 先完整跑 3 次无动态障碍基线；
- 再在不同位置加入 1～3 个静态新障碍；
- 最后加入一次受控移动障碍；
- 每次记录深度、里程计、全局/局部路径、状态、原始速度、安全速度和最终 `/cmd_vel`；
- 每次失败必须能够用 rosbag 重放，不以“再试一次没发生”代替定位原因。

通过条件建议：连续 10 次到达目标无碰撞；所有无路场景都停车；动态障碍移除后不长期残留；误停车次数和局部重规划耗时达到项目接受标准。

### 7.7 第 6 级：耐久和退化测试

连续运行 20～30 分钟，覆盖：

- 相机帧率下降和短时丢帧；
- HLoc/ICP 重定位；
- CPU/GPU 高负载；
- 浏览器连接/断开，但网页仍只回传 RGB，不回传调试点云；
- 手动网页控制抢占自动导航；
- 节点正常退出和异常退出；
- 官方遥控器/现场急停接管流程。

动态避障只修改 ROS 导航速度链，不应改动 D1 厂家遥控器协议。但“官方遥控器在 SDK 控制开启时的优先级”必须按厂家固件实测，不能把遥控器当作软件安全门的替代品。

## 8. 指标和记录表

每次测试至少记录：

| 指标 | 含义 | 初始目标/处理原则 |
| --- | --- | --- |
| 深度有效频率 | 避障实际收到的深度帧率 | 稳定不低于 10 Hz |
| 感知到停车决策延迟 | 障碍首次有效出现到安全门判停 | 初期争取不超过 250 ms，最终按制动试验收紧 |
| 最终停车净距 | 机器人最大外廓到障碍距离 | 始终大于实测安全余量 |
| 局部重规划时间 | blocked 到新路径 ready | 初期目标不超过 500 ms；期间必须保持零速 |
| 障碍清除时间 | 移走障碍到状态重新 clear | 通常 1～2 s，不能以误清除换速度 |
| 误停车率 | 无真实障碍却停车 | 按每 100 m 或每 30 分钟统计 |
| 漏检率 | 障碍进入停车区但未判停 | 安全测试中必须为 0 |
| 绕行成功率 | 有安全通路时成功接回全局路径 | 分障碍类型和光照统计 |
| 最小路径净距 | 局部路径到膨胀障碍的最小值 | 不得小于配置安全半径 |
| 资源占用 | CPU、内存、深度丢帧 | 不得拖慢 15 Hz 控制和 0.3 s 看门狗 |

测试记录应注明地图版本、代码提交、参数文件、机器人高度模式、速度上限、光照、障碍材质和操作者。否则不同批次数据不可比较。

## 11. 上线门槛与停止条件

只有满足以下条件，才能从“只停车”进入“自动绕行”：

- 相机内参、外参、frame 和时间戳全部验证；
- 10 cm～1 m 的不同速度停车试验全部通过；
- 低矮物、细腿、黑色/反光表面风险已记录并有处理策略；
- 深度、TF、里程计和节点故障全部能 fail-safe；
- 滚动障碍不会写回和污染保存地图；
- 局部路径同时通过静态地形、语义坑区和动态 3D 净空检查；
- 手动抢占、网页急停和官方遥控器现场流程已验证；
- 每次真机失败都能由日志或 rosbag 复现。

出现以下任一情况应停止真机测试并退回 `monitor_only`：

- frame 方向或尺度不确定；
- 障碍进入停车区但状态仍为 clear；
- `/cmd_vel` 在感知/TF 过期后仍保持非零；
- 障碍移走后频繁误清除、误恢复或左右振荡；
- 控制周期、深度帧率或定位频率因避障节点明显下降；
- 机器人外廓、制动距离或腿部高度模式改变但参数未重新标定。

## 12. 推荐实施顺序

1. 先采集深度、CameraInfo、`/navigation/odom` 和 TF 录包，确认频率与坐标；
2. 实现滚动 3D 体素、射线清空、时间衰减和可视化，保持 `monitor_only`；
3. 实现独立安全走廊和速度安全门，完成静止及短距离停车测试；
4. 将全局规划输出与跟随路径拆分为 `/navigation/global_path` 和 `/navigation/planned_path`；
5. 实现局部 2.5D/Hybrid A* 绕行，并用 3D 体素做最终碰撞校验；
6. 完成 2～3 m、移动障碍、10～20 m 和耐久测试；
7. 只有在纯几何方案对横穿目标明显不足时，再增加聚类跟踪和短时运动预测。

这条路线保留现有全局 3D 地形能力，也把实时避障限制在机器人周围的小范围内；出现问题时可以独立关闭局部重规划，退回“静态导航 + 实时停车”，便于安全调试和逐步验收。
